# Portfolio Experience Design

## Purpose

`docdott.com` is not intended to function as a traditional online résumé.

The portfolio should provide evidence of how cloud solutions are understood, designed, implemented, verified, and improved.

A recruiter should not have to infer engineering capability from a list of technologies.

The work should demonstrate it.

---

## The 30-Second Objective

Within the first 30 seconds, a visitor should understand three characteristics.

### 1. Consistency

The portfolio represents sustained engineering work rather than a collection of isolated demonstrations.

Projects, engagements, architecture decisions, Git history, technical writing, and lessons learned should collectively demonstrate continued development over time.

Consistency should be visible through the body of work rather than stated as a personal claim.

### 2. Architectural Judgment

Technology selection begins with the problem being solved.

The portfolio should repeatedly demonstrate the reasoning pattern:

**Business Capability → Technical Requirement → Architecture Decision → Implementation → Verification**

AWS services are implementation choices within that process, not the starting point.

### 3. Solution Orientation

Architecture has value when it produces an outcome.

Projects should therefore connect design decisions to implementation evidence, testing, verification, operational considerations, and lessons learned.

The objective is not to demonstrate an ability to configure cloud services.

The objective is to demonstrate an ability to build solutions that matter.

---

## Positioning

### Primary Message

> **Building cloud solutions around the business capabilities that matter.**

### Supporting Message

I approach cloud engineering from the problem outward.

**Understand the requirement. Design deliberately. Build securely. Verify the result.**

---

## Experience Principle

The portfolio itself should serve as engineering evidence.

A visitor reading about the architecture is simultaneously using the architecture.

`docdott.com` should therefore connect:

**Claim → Architecture → Working System → GitHub Evidence**

The website is not merely a description of engineering work.

It is part of the engineering work.

# Homepage Experience Hierarchy

## 1. Hero

**Building cloud solutions around the business capabilities that matter.**

I approach cloud engineering from the problem outward.

**Understand the requirement. Design deliberately. Build securely. Verify the result.**

Primary actions:

* Explore Engineering Work
* View GitHub
* View Resume

---

## 2. AWS Credentials

A compact certification strip should display:

* AWS Certified Cloud Practitioner
* AWS Certified Solutions Architect – Associate

The badges should reinforce credibility without dominating the page.

Supporting line:

**Certified knowledge. Applied through real engineering work.**

---

## 3. Featured Engineering Engagements

Show three to four high-value projects rather than every repository item.

Each project card should answer:

**Business Problem**

**Architecture Decision**

**Result**

**View Evidence**

Initial candidates:

* Production Web Tier
* Serverless Order System
* Linux Incident Investigation
* Cloud Engineering Portfolio Platform

---

## 4. How I Architect

Present the reasoning model visually:

**Business Capability → Technical Requirement → Architecture Decision → Implementation → Verification**

Supporting statement:

> AWS services are implementation choices. The problem comes first.

This section should immediately differentiate the portfolio from a traditional project gallery.

---

## 5. Live Cloud Architecture

Show the architecture powering `docdott.com`.

Visitors should be able to see that the portfolio itself uses:

**Route 53 → CloudFront → Private S3**

and:

**API Gateway → Lambda → DynamoDB**

Supporting controls include:

**AWS WAF, IAM, CloudWatch, and AWS Budgets**

The section should communicate:

> You are currently using one of the systems documented in this portfolio.

---

## 6. Live Application Evidence

Provide visible dynamic features:

* Visitor counter
* Engineering Guestbook
* Platform status

These features demonstrate that the portfolio is a functioning cloud application rather than a collection of static pages.

---

## 7. Engineering Principles

Feature a small number of principles earned through the work.

Examples:

> Design Before You Deploy.

> Validate Before Introducing Complexity.

> Grant workloads the minimum authority required to perform their responsibility.

> Configuration is a claim. Verification is evidence.

> Observe behavior before it becomes a bill.

---

## 8. Technical Writing

Feature the eventual Medium article about completing and extending the Cloud Resume Challenge.

The article should connect the project to the larger shift from memorizing AWS services toward designing from business capabilities.

---

## 9. Closing Call to Action

End with a concise professional invitation.

**Interested in how I approach cloud problems?**

Explore the engineering evidence, review the architecture, or start a conversation.
